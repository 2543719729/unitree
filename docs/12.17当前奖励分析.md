# 12.17 当前奖励分析（`stair_single_blind_cfg.py`）

分析对象：

- 配置文件：`unitree_rl_lab/source/unitree_rl_lab/unitree_rl_lab/tasks/locomotion/robots/g1/29dof/stair_single_blind_cfg.py`
- 奖励类：`StairBlindRewardsCfg`
- 场景：盲爬楼梯（不使用 `height_scanner`，主要依赖本体感知 + 接触力）

目标：逐项审查**所有奖励项**的合理性、可能导致的问题（尤其是 `upward_progress` 长期很低、reward 波动/阶段性下跌），并给出后续优化方向。

---

## 0. 重要口径：奖励的真实加入方式（`dt` 缩放）

Isaac Lab 的 `RewardManager` 里，每个 reward term 的加入是：

- `term_value * weight * dt`

同时日志 `Episode_Reward/<term>` 的写法是：

- `episode_sum / max_episode_length_s`

因此：

- 如果 episode 经常提前终止（例如 `bad_orientation`），即使“每步”奖励项看起来还可以，日志数值也会被 **(episode_length / max_episode_length)** 比例缩小。
- **训练阶段性掉分**有一部分是“变难/终止变早”的自然结果，不一定代表 reward 设计完全错误。

本 cfg 的时间尺度（来自 `__post_init__`）：

- `sim.dt = 0.005`
- `decimation = 4` → `step_dt = 0.02s`（策略 50Hz）
- `episode_length_s = 40s` → `max_episode_length ≈ 2000 steps`

## 2. 单项合理性审查（逐项）

### 2.1 `track_lin_vel_xy`（速度跟踪，核心驱动）

- **输出范围**：`exp(-error/std^2)`，理论 (0, 1]
- **合理性**：
  - 作为“走起来”的主驱动很合理，能抑制站桩策略。
- **潜在问题**：
  - 若地形的“最佳爬升方向”与机器人朝向/命令方向不一致，可能出现“追速度但不上楼”。
- **建议**：
  - 后期阶段可逐步把权重从速度跟踪转移到 `upward_progress` / 更直接的进展指标。

### 2.2 `track_ang_vel_z`（转向跟踪）

- **合理性**：能减少无意义转向。
- **潜在问题**：楼梯任务一般不需要显著转向，属于额外学习负担。
- **建议**：若训练不稳或 `bad_orientation` 很高，可进一步降低命令角速度范围或降低该项权重。

### 2.3 `alive`（存活）

- **合理性**：训练初期需要“先别倒”。
- **潜在问题**：与某些“静止也高分”的奖励叠加时，会强化站桩。
- **建议**：保持 1.0 合理；后期可继续降低（或与 curriculum 绑定）。

### 2.4 `upward_progress`（上升进展，任务对齐项）

- **实现要点**：
  - `instant_reward = tanh(delta_scale * clamp(Δz, 0))`
  - `progress_reward = tanh(progress_scale * clamp(z - z0, 0))`
  - 返回约 [0, 2]
- **合理性**：这是最“任务一致”的奖励项。
- **潜在问题**：
  - 若姿势/关节惩罚过强，策略不敢做出抬腿/上台阶动作，会导致该项长期接近 0。
- **建议**：保留；优化重点应放在“减少与上楼动作冲突的惩罚项”。

### 2.5 `radial_distance_progress`（径向距离进展）

- **合理性**：对倒金字塔楼梯（中心低、向外高）确实匹配。
- **关键风险（很容易导致跑偏/掉分）**：
  - 当前是“**绝对距离**”：`tanh(0.5 * distance)`。
  - 结果是：只要离开出生点后，该项会长期接近常数（饱和），甚至“站着不动也能持续吃分”。
- **建议（优先级很高）**：
  - 改为“增量式”进展：奖励 `Δdistance`（只奖变大，不奖变小），避免形成常数底座。
  - 或把它从长期 reward 改为 curriculum 指标/日志指标。

### 2.6 `base_linear_velocity`（`lin_vel_z_l2`）

- **合理性**：抑制上下颠簸。
- **潜在问题**：上台阶必然带来一定 z 速度，该项会惩罚“必要动作”。
- **建议**：
  - 若发现策略“上不去但很稳”，可进一步减小权重，或在后期阶段再加回。

### 2.7 `base_angular_velocity`（`ang_vel_xy_l2`）

- **合理性**：抑制俯仰/横滚角速度，有助于稳定。
- **潜在问题**：楼梯接触冲击会导致角速度瞬时增大，可能带来负 reward 尖峰。
- **建议**：当前权重很小，一般可保留。

### 2.8 `joint_vel`（关节速度惩罚）

- **合理性**：约束动作可控性。
- **潜在问题**：过强会让策略“走得太保守”。
- **建议**：当前较小；如果出现明显抖动，可略提高（但要配合 `action_rate`）。

### 2.9 `joint_acc`（关节加速度惩罚）

- **合理性**：抑制高频抖动。
- **潜在问题**：权重极小，实际影响可能接近 0。
- **建议**：目前不是主要矛盾，可后置处理。

### 2.10 `action_rate`（动作变化率惩罚）

- **合理性**：减少策略高频抖动。
- **潜在问题**：过强会削弱探索（尤其是早期）。
- **建议**：当前已降低到 -0.01，属于合理区间。

### 2.11 `dof_pos_limits`（软限位惩罚，风险项）

- **函数特性**：只要超 soft limit，就会产生正值；多关节叠加后可能较大。
- **潜在问题**：
  - 这是典型的“**尖峰惩罚**”来源：某次探索动作导致多个关节越界，reward 会突然很负。
  - 训练中期一旦策略开始尝试更大幅度抬腿/跨步，越界概率增大，可能出现你观察到的“奖励急剧下跌”。
- **建议（优先级高）**：
  - 进一步降低权重（例如 -0.2 ~ -0.5 区间试验）。
  - 或对该项做上限裁剪/softening（若你愿意后续改代码）。

### 2.12 `energy`（能耗）

- **合理性**：长期策略更省能。
- **潜在问题**：早期会抑制探索；但你目前权重很小。
- **建议**：可以后期再逐步加大，而不是一开始就强调。

### 2.13 `joint_deviation_arms`（手臂回正）

- **合理性**：减少手臂乱甩导致的惯性扰动。
- **潜在问题**：手臂在爬楼可能用于平衡，惩罚过强会削弱平衡能力。
- **建议**：当前 -0.1 较温和，可保留。

### 2.14 `joint_deviation_waists`（腰部回正，可能抑制必要前倾）

- **合理性**：避免腰部大幅扭动导致失稳。
- **潜在问题**：爬楼时躯干前倾/调整可能需要腰部参与；该项过强会导致“很直立但上不去”。
- **建议**：若 `upward_progress` 长期很低，可尝试降低该项权重或只约束 yaw。

### 2.15 `joint_deviation_legs`（髋 roll/yaw 回正）

- **合理性**：鼓励对称、稳定的髋部姿势。
- **潜在问题**：跨台阶时髋 roll/yaw 对摆腿很重要，惩罚过强会影响高抬腿。
- **建议**：可在后期阶段再逐步加强；或降低到 -0.3~-0.6 区间做对比。

### 2.16 `flat_orientation_l2`（保持躯干竖直，强约束）

- **合理性**：防倒、保持姿态。
- **潜在问题**：上楼通常需要一定前倾；权重 -4.0 可能过强，导致策略“宁愿不爬也要竖直”。
- **建议**：
  - 若上楼困难：优先尝试把该项降低到 -1.5~-3.0 区间。
  - 或改成“只惩罚过大倾角”的形式（需要改 reward 代码）。

### 2.17 `joint_deviation_knees`（防蹲惩罚，强冲突候选）

- **合理性**：避免“蹲着挪动”这种非理想 gait。
- **潜在问题（非常关键）**：
  - 上台阶需要显著抬腿/屈膝；该项可能直接压制必要动作。
  - 这类“形态约束”很容易让策略卡在平地走/站稳阶段。
- **建议（优先级高）**：
  - 更推荐用 `base_height_relative(only_penalize_drop=True)` 这类“惩罚蹲下/摔倒”而不过度限制屈膝的方式替代（后续可改配置）。
  - 或把 `joint_deviation_knees` 权重显著降低（例如 -0.2~-0.5）。

### 2.18 `gait`（接触相位匹配）

- **合理性**：给策略一个“像走路”的结构性先验。
- **潜在问题**：楼梯上触地相位会比平地更不规则，过强会抑制适应性。
- **建议**：当前 0.5 不算强，可保留。

### 2.19 `feet_slide`（脚滑惩罚）

- **合理性**：楼梯任务非常需要，能减少无效打滑。
- **潜在问题**：某些台阶边缘接触会产生瞬时滑动，惩罚可能增加训练噪声。
- **建议**：若策略“上不去但很稳”，可略降低；若策略经常打滑则保留。

### 2.20 `feet_clearance`（抬脚奖励，当前实现存在**重大风险**）

- **当前实现（`foot_clearance_reward`）的关键点**：
  - 使用 `exp(-Σ( (foot_z-target)^2 * tanh(v_xy) ) / std)`
  - **当脚几乎不动时**：`tanh(v_xy)≈0` → 指数项≈0 → reward≈`exp(0)=1`

- **直接后果**：
  - 机器人“站着不动/小步抖动”时该项接近满分。
  - 当策略开始真正迈步（v 变大），如果脚高没有精准到 target，高度误差会被放大，reward 会明显下降。
  - 这非常符合你观察到的：训练到某阶段“开始动了/开始探索上楼动作”→ reward 反而突然下跌。

- **另外一个明显问题**：配置注释写“目标高度从 0.20 降到 0.12”，但参数仍是 `target_height: 0.20`，存在**注释-参数不一致**。

- **建议（最高优先级）**：
  - 把该项改成“只在 swing 期间且有命令时奖励”，并避免静止给满分。
  - 形式上更稳妥的做法是“只惩罚未抬高”：例如使用 `max(threshold - foot_z, 0)` 而不是追踪固定 target。
  - 先修正 `target_height` 注释与参数不一致的问题。

### 2.21 `undesired_contacts`（非脚部接触惩罚）

- **合理性**：防止膝盖/髋/躯干撞台阶，减少摔倒。
- **潜在问题**：
  - 楼梯上偶发的非脚部擦碰可能是“有效探索”的一部分；惩罚过强会让策略不敢上。
  - 该项是“计数型”，一次接触多个 body 会叠加，可能形成负 reward 尖峰。
- **建议**：
  - 适度降低权重，或更精细地定义 body 白名单/黑名单（例如允许小腿轻微接触）。

## 3. 当前最可能导致训练问题的 4 个关键点（按优先级）

### 3.1 `feet_clearance_reward` 会奖励“静止”，并在迈步时掉分

这是最典型的“阶段性掉分/奖励急跌”触发器：

- early：站桩/小抖动 → `feet_clearance≈1` → 总 reward 看起来不错
- later：开始走/上台阶 → `feet_clearance` 降 → 总 reward 掉

### 3.2 `radial_distance_progress` 为绝对距离 → 常数底座 + 可被站桩继承

它更像“到达奖励”，不适合长期每步给。

### 3.3 “姿态/形态约束”可能压制必要上楼动作

候选冲突项：

- `flat_orientation_l2`（-4.0）
- `joint_deviation_knees`（-0.9）
- `joint_deviation_waists`（-0.8）

这几项叠加很容易得到“很直立很稳但不上楼”。

### 3.4 尖峰惩罚导致训练不稳定

候选尖峰项：

- `dof_pos_limits`
- `undesired_contacts`

这两类往往是“某一次动作探索 → reward 暴跌 → PPO 更新方向被破坏”的来源。

## 4. 后续优化方向（建议路线图）

### P0（必须先做，最可能立刻改善）

- **修 `feet_clearance` 设计**：避免静止给满分；建议加 gating（命令>阈值 + swing 相位）
- **把 `radial_distance_progress` 改为增量式**（或改为 curriculum 指标而非长期 reward）
- **对尖峰惩罚做“降权/裁剪”策略**：优先从降低 `dof_pos_limits`、`undesired_contacts` 权重开始

### P1（提升上楼成功率）

- 逐步降低“形态约束”项（`knee/waist/flat_orientation`），观察 `upward_progress` 是否上升
- 用“高度下降惩罚”替代“屈膝惩罚”（例如 `base_height_relative(only_penalize_drop=True)`）来防蹲但不抑制抬腿

### P2（提升风格与能耗）

- 在策略已经能稳定上楼后，再逐步提高 `energy` / `joint_vel` / `action_rate` 约束，形成更平滑、省电的步态
